User stories:

    • As host, I want my entire attendee list copied to the check-in system reliably before the event starts.
    • As Cloud Infra person, I want the sync to be idempotent so re-runs are safe.

Acceptance criteria:

Given Pankaj's POST /internal/checkin/prepare/{event_id} endpoint is invoked (from B1's "Prepare" click)
When the endpoint runs
Then:
  - The endpoint queries ExplaraX core Postgres for all attendees of event_id
  - Generates a fresh per-event HMAC key (or reuses an existing one stored in ExplaraX)
  - Calls Supabase admin API to upsert attendees in batches of 1,000

Given the upsert is in progress
When a batch is sent
Then it includes only fields specified in tech spec Section 4: ticket_id, event_id, attendee_name, ticket_type, company, designation, seat, qr_token, metadata. **No email, phone, or payment data.**

Given an attendee already exists in Supabase (re-sync case)
When the upsert runs
Then existing check-in fields (checked_in_at, checked_in_gate, etc.) are preserved; only attendee metadata is refreshed.

Given the sync completes
When all batches succeed
Then a record is written to ExplaraX core marking the event as "prepared" with a timestamp.

Given a batch fails (network, Supabase error)
When the failure is detected
Then the job retries with exponential backoff up to 3 times before surfacing an error to the host.

Test scenarios for Kiro:

    • Sync 100 attendees → completes in <30 seconds
    • Sync 10K attendees → completes in <5 minutes, batched
    • Re-sync after 50 new tickets sold → only 50 new rows added; 9,950 existing rows untouched
    • Network drops between batches → resumes from the failed batch on retry
    • Sync triggered twice in parallel → second invocation is no-op (advisory lock or status check)
