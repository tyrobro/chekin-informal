User stories:

    • As Pankaj, I want a clean, well-defined endpoint Supabase can call without ambiguity.
    • As host, I want my main ExplaraX dashboard to reflect check-in status after the event.

Acceptance criteria:

Given Supabase has finished an event and triggers sync-back
When the POST hits /internal/checkin/sync-back
Then the request includes:
  - Authentication header (shared secret)
  - JSON body: event_id, batch of check-in records {ticket_id, checked_in_at, checked_in_gate, checked_in_by, checkin_method}

Given the request is authenticated
When the body is processed
Then each record updates the corresponding ticket in ExplaraX core's `tickets` table with check-in fields, idempotent on ticket_id.

Given a record references a ticket_id that does not exist in ExplaraX
When the update is attempted
Then the record is logged in a `checkin_sync_errors` table for review, the overall sync continues.

Given the entire batch is processed
When all records have been attempted
Then a response is returned to Supabase with counts: succeeded, failed, total.

Given the webhook receives the same batch twice
When idempotency is checked
Then duplicates are detected (by ticket_id + checked_in_at) and skipped without error.

Test scenarios for Kiro:

    • Sync-back of 10K check-ins → completes within 2 minutes
    • Sync-back with 50 invalid ticket_ids → 9,950 succeed, 50 logged for review
    • Sync-back called twice with the same payload → second call is a no-op

## Additional Implementation Context

### API Contract

Endpoint:

POST /internal/checkin/sync-back

Authentication:

Authorization: Bearer {SHARED_SECRET}

Content-Type: application/json

Request:

```json
{
  "event_id": "TCS-10K-2026",
  "batch_id": "uuid",
  "records": [
    {
      "ticket_id": "E4CACB-177",
      "checked_in_at": "2026-06-15T09:14:23Z",
      "checked_in_gate": "Gate A",
      "checked_in_by": "staff-uuid",
      "checkin_method": "qr_scan"
    }
  ]
}
```

Response:

```json
{
  "batch_id": "uuid",
  "succeeded": 998,
  "failed": 2,
  "failures": [
    {
      "ticket_id": "BAD-001",
      "reason": "ticket not found in ExplaraX"
    }
  ]
}
```

### Architecture Requirements

* Follow Service Layer Pattern.
* Controllers must remain thin.
* Business logic belongs in services.
* Database access belongs in repositories.
* Use DTOs for request validation and service contracts.
* Use dependency injection.
* Use strict typing.

### Idempotency Requirements

* Sync-back must be idempotent.
* Receiving the same batch multiple times must be a no-op.
* Duplicates are identified using:

  * ticket_id
  * checked_in_at
* Duplicate records should be skipped without error.

### Error Handling

If a ticket_id does not exist:

* Continue processing remaining records.
* Log the failure into checkin_sync_errors.
* Include the failure in the response payload.

Suggested columns:

* event_id
* ticket_id
* reason
* payload
* created_at

### Performance Requirements

* Support batches up to 10,000 records.
* Complete processing within 2 minutes.
* Process records in chunks when appropriate.
* Use bulk database operations where possible.

### Logging

Use structured JSON logging.

Include:

* event_id
* batch_id
* ticket_id
* request_id / correlation_id

### Testing Requirements

Create:

* Unit tests for services.
* Integration tests for API endpoint.
* Idempotency tests.
* Invalid ticket tests.
* Large batch tests.
