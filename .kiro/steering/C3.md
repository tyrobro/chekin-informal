User stories:

    • As host, I want sync-back to happen automatically when my event ends; I shouldn't have to click anything.
    • As host, I want a manual override if automatic sync fails.

Acceptance criteria:

Given an event's end_time has passed
When a Supabase scheduled function runs (every 5 minutes)
Then it identifies events whose end_time is in the past and whose sync_status is not "complete", and triggers sync-back for each.

Given sync-back is triggered for an event
When it runs
Then it queries Supabase for all checked_in attendees, batches them (1,000 per batch), and POSTs each batch to ExplaraX's /internal/checkin/sync-back endpoint.

Given all batches succeed
When the final response is received
Then the event's sync_status in Supabase is marked "complete" and the event status in the host's dashboard transitions from "Completed (Syncing)" to "Completed".

Given any batch fails permanently (after retries)
When the failure is final
Then sync_status is marked "failed", an alert is emitted to Cloud Infra monitoring (I8), and the host sees a "Retry sync" button.

Given the host clicks "Retry sync"
When the retry runs
Then the sync resumes from the last successful batch.

Test scenarios for Kiro:

    • Event ends, sync-back runs within 5 minutes → all records land in ExplaraX
    • Event ends while Supabase scheduled function is in maintenance → sync runs on next scheduled tick, no data loss
    • Manual retry after partial failure → resumes correctly, no duplicates

### Supabase Scheduled Function

A scheduled job SHALL run every 5 minutes and:

1. Find events where:

```sql
end_time < NOW()
AND sync_status <> 'complete'
```

2. Fetch all checked-in attendees for each eligible event.

3. Partition records into batches of 1,000.

4. POST each batch to:

```text
POST /internal/checkin/sync-back
```

using the existing C2 contract.

---

### Resume and Retry Behaviour

The system SHALL support resumable syncs.

For each event, persist:

* `sync_status`
* `last_successful_batch`
* `completed_at`
* `error_message`

If batch N fails permanently:

* Mark `sync_status = 'failed'`
* Emit monitoring alert
* Allow host-initiated retry

Manual retry SHALL resume from `last_successful_batch + 1` and SHALL NOT restart from batch 1.

---

### Idempotency Rules

C3 SHALL rely on C2's existing idempotency guarantees and SHALL NOT implement duplicate ticket-update logic.

Retrying the same batch multiple times MUST produce the same final state.
